# Introduction: Test Management Assistant

**Context – SAP Migration & Modernization Assistants**

Before we jump into the hands-on, a quick word on context, because what you're about to use is not an isolated feature.

SAP has developed seven AI-powered assistants for Migration and Modernization scenarios, built to help customers move from SAP ECC to S/4HANA Cloud Private Edition faster and with significantly less manual effort:

<br><img src="exercises/ex_intro/images/intro_7_assistants.png" style="border:1px solid #ddd;border-radius:4px;" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>01 – Seven SAP Migration & Modernization Assistants</em></p>

The **Test Management Assistant** is one of these seven, and Test Management is an area where the shift from manual to AI-driven work matters most:

End-to-end test management for SAP migrations and modernizations is still heavily dependent on business and IT personnel. It is a consistent cost driver across transition projects, and complexity grows with every regression cycle: more scenarios, more variants, more manual effort.

The Test Management Assistant targets the upstream side of this: the preparation of manual end-to-end testing. It applies AI to test scoping, test case writing, and test data preparation; these are the stages where expert effort is highest and where days of work can be compressed into minutes of guided review.

Test execution itself is outside the current scope of the assistant. That stage is covered by the partner ecosystem: Tricentis, SAP's strategic partner for test automation, provides execution capabilities that complement the AI-driven preparation in SAP Cloud ALM.

## What is the Test Management Assistant?

The Test Management Assistant is not a single AI feature; it's a pipeline of four specialized agents, each transforming a stage of manual Test Preparation into an AI-driven capability:

<br><img src="exercises/ex_intro/images/intro_agent_architecture.png" style="border:1px solid #ddd;border-radius:4px;" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>02 – Test Management Assistant: four-agent pipeline</em></p>

The Scoping, Preparation, and Test Data Management agents (Phase 1\*) have been released and are currently in Early Adopter Care with selected customers. GA is targeted before the end of this year. The Test Execution Quality Management agent is planned for 2027\*\*.

> *\* Partly available; \*\*planned functionality. Subject to change by SAP at any time without notice.*

> **Today's hands-on covers the three agents available today**: Scoping, Preparation, and Data Management. Execution Management is on the roadmap.

## 3.2 – What's happening in the background?

<br><img src="exercises/ex2/images/ex2_03_scoping_agent_flow.png" style="border:1px solid #ddd;border-radius:4px;" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>25 – Scoping agent methodology</em></p>

> **The scoping agent applies a structured methodology:**
> 1. It resolves the process name, *Requirements*, and *User Stories* to exact identifiers in SAP Cloud ALM
> 2. It validates that the required input exists; if not, it blocks and returns clear instructions on what to fix
> 3. It classifies each input: process scope variants or detailed reference steps
> 4. It enriches the scope with SAP standard test baselines and extracts Acceptance Criteria from your linked content
> 5. It scores each *Scope Item* for completeness, ranks items by priority, and flags coverage gaps
> 6. It presents the result for your review and sign-off; no downstream work starts without your approval (the "Human in the Loop", or HITL, Gate 1)
>
> This is the same analysis a skilled test architect would do, but compressed from hours into minutes.

---

## 3.3 – Manual Scoping Exercise

While you wait for the agent, try a structured manual scoping exercise.

Return to the Processes app and for the *BJ5_simple* process, think through these dimensions (a piece of paper to jot notes works fine):

| Dimension | Your Answer |
|---|---|
| What are the main **process paths** (happy path + variants)? | |
| What **acceptance criteria** can you identify from the *User Stories* and *Requirements*? | |
| How many distinct **apps/UIs** are involved? | |
| How many **roles** participate? | |
| Which steps have **blocking conditions** worth testing? | |
| What **error scenarios** can you imagine that should be covered? | |

> Hint: The BJ5 process involves 2 roles (Production Planner and Warehouse Clerk) and spans the full make-to-stock cycle from production order creation to finished goods receipt. There is 1 critical quality gate where output is assessed before goods receipt, and a separate failure path for scrap and replenishment.

## 3.4 – Review the Scoping Agent's Work

**1.** When the agent is ready, it replies directly in the Joule chat window with a **Test Scope Summary**. The response is detailed; best switch Joule to **full-screen mode** first using the **expand icon** in the top-right of the Joule panel.

The response typically gives you:

- **Process context**: the *Solution Process*, flow diagram, and applicable countries it resolved
- A **summary of identified process flow paths**, reflecting any splits or variants in the process structure
- An overview of the **items it ingested** (your *Requirement* and the 7 *User Stories*)
- Related **standard process procedures** retrieved from the SAP Enterprise Architecture Reference Library (EARL)
- A conclusive list of **acceptance criteria** derived from all of the above, augmented with patterns from SAP's standard process baselines

<br><img src="exercises/ex2/images/ex2_04_scope_result.png" style="border:1px solid #ddd;border-radius:4px;" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>26 – Test Scope Summary in Joule</em></p>

After the response, the agent asks you whether to confirm the scope as is or revise it.

> **HITL (Human in the Loop) Gate 1: Test Scope Summary.** This is the first checkpoint in Test Management Assistant's agentic workflow. The agent stops, presents its detailed structured analysis, and waits for your review and sign-off. Nothing proceeds until you confirm.

**2.** Before making that decision, take a few minutes to work through the proposed scope. For each item, check:
- **Name and description**: does it clearly describe what's being tested?
- **Linked acceptance criteria**: is it traceable back to a *User Story* or *Requirement*?

# Chapter 6 – Generate Test Data

Good test data may be one of the most underestimated parts of Test Preparation. A single wrong value (an invalid material, the wrong plant, a date outside the planning horizon) is enough to make a test fail for the wrong reasons, wasting time and masking real *Defects*. It is also a recurring burden: even for established *Test Cases*, data values get consumed during Test Execution (orders confirmed, stock moved, documents created) and must be refreshed before the next run. Yet gathering valid, consistent test data for a business process like BJ5 traditionally demands expert knowledge of both the process and the system configuration.

**Prerequisite:** You have completed [Chapter 5](../ex4/README.md); *Test Cases* have been generated for the BJ5 process and are visible in Test Preparation.

---

## What You'll Do

In this chapter you'll work with the **Test Data Management Agent**. In its current Phase 1 form, the agent reads a *Test Case* and extracts every parameter placeholder: the fields where a tester will need to provide a specific value to execute the step. It classifies them by data category; for parameters that are constant across the project (such as company code, plant, and client), it applies the known project-level values automatically so the tester does not need to look them up.

The current Phase 1 capability is the foundation for a progressively richer roadmap. Future phases will connect the agent to a live S/4HANA system: first to suggest values that actually exist in the test environment, then to propose new master data records where the right values do not yet exist, modelled on patterns from a productive system. The final step will extend to writing data directly into target systems; not only master data but also transient data: the prerequisite document chains (inquiry, offer, order, delivery) needed for *Test Cases* that begin mid-flow in a business process.

For now, Phase 1 turns unstructured Test Step text into a structured, actionable parameter checklist.

## 6.1 – Understanding the Agent

The diagram below shows the full pipeline of the Test Data Management Agent in Phase 1:

## 6.4 – Review the Agent's Output

When the agent returns, it presents a structured table of all data parameters identified in the *Test Case*, grouped into four categories.

**Organisational data**
The fixed organisational frame: sales organisation, distribution channel, division, and dependent org units such as plant and storage location. These values are typically re-usable across *Test Cases* in a project, and the agent applies them automatically from the project context wherever possible.

**Master data**
Objects that must exist in the system before the test can run: materials valid for the sales area and plant, business partners in the correct role (for example: sold-to party, ship-to, payer), and any dependencies between them. A sold-to party determines which ship-to and payer are valid; a material type determines which item category is auto-assigned.

**Configuration data**
System settings that affect process behaviour: pricing procedures, document types, workflow configurations, authorisation roles. These rarely change between test runs but must be verified to exist and be correctly set up before testing.

**Transactional data**
Values that are either chosen by the tester at runtime or generated on the fly during execution: quantities, dates, and document numbers (order numbers, delivery numbers, production order IDs) that only exist after a preceding step has been completed.

**Why dependencies matter**

The agent does not just list parameters; it explains which values drive which others. This is more valuable than it first appears. Consider a quantity of "10" entered in a production order step: taken in isolation it looks arbitrary. Trace it forward through the process and that same quantity must arrive at a picking step where the storage location needs to hold sufficient stock. If it does not, the test will fail for the wrong reasons: not a *Defect*, but a data setup problem. Understanding these dependencies upfront is the prerequisite for future agent phases to run automated checks and resolve such blocking conditions before a test is even started.

| **Test planning** | Drafted a *Test Plan* entry manually for one *Scope Item* | Preparation Agent structured the full scope into a *Test Plan* with roles, paths, and Acceptance Criteria |
| **Test cases** | Wrote one *Test Case* manually in a template | Preparation Agent wrote complete, executable *Test Cases* for the confirmed scope |
| **Test data** | Identified parameter placeholders in a *Test Case* step by step | Test Data Management Agent extracted and classified all parameters, explained dependencies |

What would have taken a test team several days, end to end, was completed by the agents in the time it took you to work through the manual exercises. Not as a replacement for your judgment, but as the first draft you review rather than the blank page you fill.

**The shift:** you moved from *producing* test artifacts to *reviewing* them. The expert role does not disappear; it changes:
Instead of writing Test Steps, you validate whether the agent got the scenario right.
Instead of looking up master data, you confirm whether the classifications make sense.
That judgment is irreplaceable; the mechanical production of structured content is not.

## 7.2 – What's Coming Next

The capabilities you worked with today are Phase 1 of the Test Management Assistant in SAP Cloud ALM. The roadmap has three main directions.

**Scoping Agent: broader input sources**

Today the Scoping Agent reads from SAP Cloud ALM. In future waves it will be able to consume additional input types: Jira *Requirements*, Signavio process models, output from other SAP AI assistants in the multi-model architecture (MMA), and more. Scoping will become source-agnostic and will work across the landscape your project actually uses, not just what lives inside Cloud ALM.

**Test Data Management Agent: from identification to execution**

Today the agent identifies and classifies parameters. The next phases extend this into active data management: reading existing data from connected S/4HANA systems, suggesting values from productive data that fit the test context, and eventually writing clean test data directly into test systems before execution. This closes the loop from "what do I need?" to "the data is ready".

**Managing execution of tests: from completed to signed off**

Formal completion and genuine test validation are not the same thing; that gap is invisible in execution statistics and only surfaces at go-live. The next agent aims to close it: monitoring execution quality continuously, verifying that Test Steps were documented rather than clicked through, detecting anomalies such as suspiciously high pass rates relative to known system issues, and evaluating whether reported *Defects* carry enough detail for proper resolution. When the checks pass, it will produce a structured test report and a full *Scope Item* → *Test Case* → result traceability matrix, ready for the Test Manager's approval and sign-off.

## 7.3 – Key Takeaways

1. **This is not a separate tool; it binds into Cloud ALM.** Everything generated lives in Cloud ALM Test Management structures: *Test Plans*, *Test Cases* with tabs for content, relations, and references; notifications; traceability links. The agents work within and strengthen the existing SAP Cloud ALM architecture, not alongside it. Your test team's existing workflows, reports, and integrations remain intact.

2. **AI enhances what is already there.** The agents worked because the content was in the system: linked *Requirements*, *User Stories* with Acceptance Criteria, a process model. AI leverages existing structured content; it does not create quality from nothing. Investing in good process documentation and structured *Requirements* pays off twice.

3. **Human judgment is the irreplaceable layer.** Every agent in the pipeline includes a human review gate. The agents produced the first draft; you provided the quality check. Catching a role mismatch, a missing precondition, a *Scope Item* that does not belong: that is the test expert's contribution, and it matters as much as ever.

4. **Traceability is what makes it trustworthy.** The chain runs in two directions at once. Every *Test Case* links to the *Test Plan* and the scope; every *Scope Item* in that scope links to the process, the *User Stories*, and the Acceptance Criteria that defined it. These two structures meet at scope, which means a test result traces all the way back to a specific process path and the acceptance criterion it was designed to prove. When a test passes, you know what passed, what it means for the process, and which criterion it covers. That chain is what allows you to demonstrate testing assurance to auditors, project managers, and stakeholders with confidence.
