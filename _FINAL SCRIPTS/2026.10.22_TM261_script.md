# Introduction: Test Management Assistant

**Context – SAP Migration & Modernization Assistants**

Before we jump into the hands-on, a quick word on context, because what you're about to use is not an isolated feature.

SAP has developed seven AI-powered assistants for Migration and Modernization scenarios, built to help customers move from SAP ECC to S/4HANA Cloud Private Edition faster and with significantly less manual effort:

<br><img src="exercises/ex_intro/images/intro_7_assistants.png" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>01 – Seven SAP Migration & Modernization Assistants</em></p>

The **Test Management Assistant** is one of these seven, and test management is an area where the shift from manual to AI-driven work matters most:

| Current State | Future State |
|---|---|
| E2E Test Management is still heavily dependent upon business and IT personnel; it's a cost driver for transitions. | AI automates test scope, cases, data, execution and validation across the test stages. |
| Regression scenarios increase complexity and manual effort consistently and beyond implementation phases. | Continuous validation reduces effort and user dependency, links & limits test scope to changes occurring. |

The TMA targets the upstream side of this: the preparation of manual end-to-end testing. It sits at the quality gate of every migration, and as you'll see today, it's where AI can compress days of manual work into minutes of guided review.

## 3.2 – What's happening in the background?

<br><img src="exercises/ex2/images/ex2_03_scoping_agent_flow.png" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>25 – Scoping agent methodology</em></p>

> **The scoping agent applies a structured methodology:**
> 1. It resolves the process name, requirements, and user stories to exact identifiers in SAP Cloud ALM
> 2. It validates that the required input exists; if not, it blocks and returns clear instructions on what to fix
> 3. It classifies each input: process scope variants or detailed reference steps
> 4. It enriches the scope with SAP standard test baselines and extracts acceptance criteria from your linked content
> 5. It scores each scope item for completeness, ranks items by priority, and flags coverage gaps
> 6. It presents the result for your review and sign-off; no downstream work starts without your approval (the "Human in the Loop", or HITL, Gate 1)
>
> This is the same analysis a skilled test architect would do, but compressed from hours into minutes.

---

## 3.3 – Manual Scoping Exercise

While you wait for the agent, try a structured manual scoping exercise.

Return to the Processes app and for the *BJ5_simple* process, think through these dimensions (a piece of paper to jot notes works fine):

| Dimension | Your Answer |
|---|---|
| What are the main **process paths** (happy path + variants)? | |
| What **acceptance criteria** can you identify from the user stories and requirements? | |
| How many distinct **apps/UIs** are involved? | |
| How many **roles** participate? | |
| Which steps have **blocking conditions** worth testing? | |
| What **error scenarios** can you imagine that should be covered? | |

> Hint: The BJ5 process involves 2 roles (Production Planner and Warehouse Clerk) and spans the full make-to-stock cycle from production order creation to finished goods receipt. There is 1 critical quality gate where output is assessed before goods receipt, and a separate failure path for scrap and replenishment.

## 3.4 – Review the Scoping Agent's Work

**1.** When the agent is ready, it replies directly in the Joule chat window with a **Test Scope Summary**. The response is detailed; best switch Joule to **full-screen mode** first using the **expand icon** in the top-right of the Joule panel.

The response typically gives you:

- **Process context**: the solution process, flow diagram, and applicable countries it resolved
- A **summary of identified process flow paths**, reflecting any splits or variants in the process structure
- An overview of the **items it ingested** (your requirement and the 7 user stories)
- Related **standard process procedures** retrieved from the SAP Enterprise Architecture Reference Library (EARL)
- A conclusive list of **acceptance criteria** derived from all of the above, augmented with patterns from SAP's standard process baselines

<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>26 – Test Scope Summary in Joule</em></p>

After the response, the agent asks you whether to confirm the scope as is or revise it.

> **HITL (Human in the Loop) Gate 1: Test Scope Summary.** This is the first checkpoint in Test Management Assistant's agentic workflow. The agent stops, presents its detailed structured analysis, and waits for your review and sign-off. Nothing proceeds until you confirm.

**2.** Before making that decision, take a few minutes to work through the proposed scope. For each item, check:
- **Name and description**: does it clearly describe what's being tested?
- **Linked acceptance criteria**: is it traceable back to a user story or requirement?
- **Role separation**: are Production Planner tasks and Warehouse Clerk tasks kept in separate test cases?
- **Coverage**: does the overall set cover the happy path (P1), the quality gate failure path (P2), and the scrap/replenishment scenario?

> **Compare with your manual notes from Step 3.3:** Did the agent catch everything you identified? Or did it find things you missed? That's exactly the kind of task AI agents excel at: ingesting text, inferring structure, and surfacing patterns at speed.

## 3.5 – Refine the Scope in Joule

Let's not just accept the scope as is. Joule lets you refine it through conversation, and this is the moment to apply your focus on role switches and shape the scope accordingly.

> **Note for participants sharing a system:** In a real-life scenario you'd typically start with the full E2E process before narrowing down. The reason for this tweak is twofold: first, it lets you experience how to shape agent output through a simple conversation; and second, the agents run on shared infrastructure and we want to avoid overloading the system with heavy concurrent calls. So we recommend limiting the scope to **user stories 5, 6, and 7** (the quality gate, goods receipt, and failure path), where the handoff from Production Planner to Warehouse Clerk happens.

Two options are available; as you'll see, the second is the more direct one.

**Option 1: Use the built-in "Revise Scope" shortcut**

Click the **Select** button in the Joule output panel, then choose **Revise Scope** from the dropdown. This sends a built-in prompt ("No, let me revise the scope" or similar) to the agent, which then asks you what you'd like to change. You'd still need to type your refinement in the follow-up message, making it identical to Option 2 but with one extra round-trip.

**Option 2: Write your own prompt**

You can also type your refinement directly in the Joule chat window. Navigate to user stories US-05, US-06, and US-07 and note their Display IDs (format: `3-xxx`), then use a prompt like:

> "Focus on user stories **[enter the Display IDs]**. In particular take care of roles and create test cases which do NOT cross multiple roles."

<br><img src="exercises/ex2/images/ex2_05_refine_scope.png" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>27 – Refinement prompt: focusing on three user stories</em></p>

You may try other refinements too:
- **Narrow the scope:** "Remove user stories 1–4 from the scope for now; focus only on the quality gate, goods receipt, and scrap path."
- **Narrow by role:** "Drop the Production Planner for now, and consider only the process steps relevant for the Warehouse Clerk."

The agent re-runs its scoping logic and returns faster than the first pass. It presents the revised scope and pauses for your sign-off again. This time, click **Confirm** to accept the scope and move to the next stage.

# Chapter 6 – Generate Test Data

Good test data is one of the most underestimated parts of test preparation. A single wrong value (an invalid material, the wrong plant, a date outside the planning horizon) is enough to make a test fail for the wrong reasons, wasting time and masking real defects. Yet gathering valid, consistent test data for a business process like BJ5 traditionally demands expert knowledge of both the process and the system configuration.

**Prerequisite:** You have completed [Chapter 5](../ex4/README.md); test cases have been generated for the BJ5 process and are visible in Test Preparation.

---

## What You'll Do

In this chapter you'll work with the **Test Data Management Agent**. In its current Phase 1 form, the agent reads a test case and extracts every parameter placeholder: the fields where a tester will need a specific system value to execute the step. It classifies them by data category and applies fixed project-level values (company code, plant, client) automatically.

This is the foundation for a longer roadmap: future phases will suggest actual values retrieved from test or productive systems, and eventually write clean test data directly into target systems. For now, Phase 1 turns unstructured test step text into a structured, actionable parameter checklist.

---

## 6.1 – Understanding the Agent

The diagram below shows the full pipeline of the Test Data Management Agent in Phase 1.

<br><img src="exercises/ex5/images/ex5_01_tdm_agent_flow.png" />
<p style="font-size:9pt;color:#888;margin-top:-0.5em"><em>38 – Test Data Management Agent: Phase 1 pipeline</em></p>

| Stage | What happens |
|---|---|
| **INPUT** | A test case ID or title, provided by the tester or passed from the Preparation Agent |
| **Fetch test case** | Reads the test case and all its activity steps from SAP Cloud ALM via MCP (TL102). If the test case is not found, has no activities, or the text is empty, the agent stops and asks you to verify the input. |
| **Extract parameters** | Identifies every required SAP business object and field value from the instruction text; every line of "Enter Material…" or "Select Plant…" becomes a structured parameter entry. |
| **Classify parameters** | Labels each parameter by category: **Org Data · Master Data · Config Data · Transactional Data** |
| **Apply project context** | Obtains fixed values (company code, plant, client) from the Cloud ALM project record automatically |
| **OUTPUT** | A read-only parameter table per category; structured guidance for the tester who then locates the actual values in the system |

> **Phase 1 scope note:** The agent identifies and classifies parameters; it does not yet look up or suggest actual system values. The tester uses the output as a structured checklist.

---

## 6.2 – Identify the Parameters in Your Test Case

Before triggering the agent, try it yourself. Open one of your generated test cases in Test Preparation, go to the **Content** tab, and read through the test steps. For each step, note every place where the tester will need to enter a specific value.

Look for patterns like these:

- **Material**: `<replacement material number>`; must exist in the system
- **Plant**: `<plant>`; the plant where the production operation takes place
- **Order Type**: PP01; a configuration value, already fixed here
- **Total Qty**: `<required quantity>`; must be valid for the material and order
- **Basic Finish Date**: `<planned finish date>`; must fall within the planning horizon

For a make-to-stock production and warehousing process like BJ5, you'll typically also encounter:

- **Company code**: fixed from the project configuration
- **Work center**: must exist in the plant and be assigned to the correct cost center
- **Storage location**: must be valid for the plant and movement type
- **Production order number**: a transactional reference that only exists after the order is created
- **Confirmed quantity**: depends on the output of a prior step

Note the distinction: some values are fixed (company code, plant), some are looked up once before the test (material, work center), and some are only generated at runtime (production order number). This is exactly the classification the agent applies.

## 6.3 – Trigger the Data Agent

Unlike the previous agents, the Test Data Management Agent does not start automatically after test case generation. This is intentional: test data is a separate output, used alongside test case steps rather than embedded in them. A test case describes *what* to do; test data provides *with what* to do it. These two artefacts have different lifecycles in SAP Cloud ALM, and the decision of when to enrich a test case with data is typically made by the person preparing for execution; in many projects initially a key user, and later the tester directly.

There is also a practical reason: the generated test cases need to be processed and indexed by Cloud ALM before the agent can read them. Starting a fresh Joule conversation ensures a clean context.

## 6.4 – Review the Agent's Output

When the agent returns, it presents a structured table of all data parameters identified in the test case, grouped into four categories.

**Organisational data**
The fixed organisational frame: company code, sales organisation, distribution channel, division, and dependent org units such as plant and storage location. These values are typically the same across all test cases in a project and are applied automatically from the project context wherever possible.

**Master data**
Objects that must exist in the system before the test can run: materials valid for the sales area and plant, business partners in the correct role (for example: sold-to party, ship-to, payer), and any dependencies between them. A sold-to party determines which ship-to and payer are valid; a material type determines which item category is auto-assigned.

**Configuration data**
System settings that affect process behaviour: pricing procedures, document types, workflow configurations, authorisation roles. These rarely change between test runs but must be verified to exist and be correctly set up before testing.

**Transactional data**
Values that are either chosen by the tester at runtime or generated on the fly during execution: quantities, dates, and document numbers (order numbers, delivery numbers, production order IDs) that only exist after a preceding step has been completed.

**Why dependencies matter**

The agent does not just list parameters; it explains which values drive which others. This is more valuable than it first appears. Consider a quantity of "10" entered in a production order step: taken in isolation it looks arbitrary. Trace it forward through the process and that same quantity must arrive at a picking step where the storage location needs to hold sufficient stock. If it does not, the test will fail for the wrong reasons: not a defect, but a data setup problem. Understanding these dependencies upfront is the prerequisite for future agent phases to run automated checks and resolve such blocking conditions before a test is even started.

## 7.2 – What's Coming Next

The capabilities you worked with today are Phase 1. The roadmap has three main directions.

**Scoping Agent: broader input sources**

Today the Scoping Agent reads from SAP Cloud ALM. In future waves it will be able to consume additional input types: Jira requirements, Signavio process models, output from other SAP AI assistants in the multi-model architecture (MMA), and more. Scoping will become source-agnostic and will work across the landscape your project actually uses, not just what lives inside Cloud ALM.

**Test Data Management Agent: from identification to execution**

Today the agent identifies and classifies parameters. The next phases extend this into active data management: reading existing data from connected S/4HANA systems, suggesting values from productive data that fit the test context, and eventually writing clean test data directly into test systems before execution. This closes the loop from "what do I need?" to "the data is ready".

**Test Management Agent: staying on top of the project**

The pipeline is not complete without the management layer. A dedicated agent for test managers is in development to support project oversight: tracking progress against timelines, handling the integration with external test execution automation providers, and processing feedback from execution runs including defects and retest cycles. The goal is a closed loop from test preparation through execution to defect management.

---

## 7.3 – Key Takeaways

1. **AI enhances what is already there.** The agents worked because the content was in the system: linked requirements, user stories with acceptance criteria, a process model. AI amplifies existing structured content; it does not create quality from nothing. Investing in good process documentation and structured requirements pays off twice.

2. **Human judgment is the irreplaceable layer.** Every agent in the pipeline includes a human review gate. The agents produced the first draft; you provided the quality check. Catching a role mismatch, a missing precondition, a scope item that does not belong: that is the test expert's contribution, and it matters as much as ever.

3. **This is not a separate tool; it binds into Cloud ALM.** Everything generated lives in Cloud ALM Test Management structures: test plans, test cases with tabs for content, relations, and references; notifications; traceability links. The agents work within and strengthen the existing SAP Cloud ALM architecture, not alongside it. Your test team's existing workflows, reports, and integrations remain intact.

4. **Traceability is what makes it trustworthy.** Every artifact in the chain links back to its source: test case to test plan, plan to scope, scope to user story, user story to requirement, requirement to process. When a test passes, you can trace exactly what was proven and which acceptance criterion it covers. That chain is what allows you to demonstrate testing assurance to auditors, project managers, and stakeholders with confidence.
